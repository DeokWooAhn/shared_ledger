# Firestore 데이터 구조와 권한

규칙 원본은 [`firestore.rules`](../firestore.rules), 규칙 테스트는 [`firestore-tests/`](../firestore-tests).
이 문서와 규칙이 어긋나면 규칙이 기준이다.

## 역할

| 역할 | 누가 | 할 수 있는 것 |
|---|---|---|
| 관리자(owner) | 가계부를 만든 사람, 가계부마다 한 명 | 읽기·쓰기, 이름 변경, 구성원 역할 변경·내보내기, 초대 만들기·지우기, 가계부 삭제 |
| 편집자(editor) | 초대로 들어온 사람 | 읽기·쓰기, 스스로 나가기 |
| 보기 전용(viewer) | 초대로 들어온 사람 | 읽기, 스스로 나가기 |

- 커플·부부 가계부라 **한 가계부에는 두 명까지** 들어온다. 관리자 한 명과 초대로 들어온 한 명이다(규칙의 `maxMembers()`, 앱의 `ledgerMaxMembers`).
- 구성원은 **초대 코드로만** 들어온다. 관리자도 다른 사람을 직접 추가할 수 없다.
- 관리자는 자기 역할을 내려놓을 수 없다. 관리자 넘기기는 나중에 만든다.

## 컬렉션

```
ledgers/{ledgerId}
  members/{id}
  categories/{id}
  paymentMethods/{id}
  templates/{id}
  months/{yyyy-MM}/
    incomes/{id}
    planned/{templateId}
    extras/{id}
    cardBills/{id}
  activity/{id}
invites/{code}
holidays/{yyyy}
```

### `ledgers/{ledgerId}`

| 필드 | 타입 | 설명 |
|---|---|---|
| `name` | string (1~40자) | 가계부 이름 |
| `ownerUid` | string | 관리자 uid |
| `roles` | map uid → `'editor'` \| `'viewer'` | 관리자를 뺀 구성원의 역할 |
| `memberUids` | list<string> | 관리자 + `roles`의 uid 전부. '내 가계부 목록' 조회(`array-contains`)용. 두 명까지 |
| `inviteCode` | string (선택) | 마지막으로 참여에 쓰인 초대 코드. 참여 규칙 확인용 |
| `months` | list<string> (선택) | 항목이 들어간 적 있는 달(`2026-10`). 요약·항목 탭은 이 달과 이번 달만 오간다. 없으면 아직 모으지 않은 가계부 |
| `createdAt`, `updatedAt` | timestamp | 서버 시간 |

`memberUids`는 항상 `ownerUid` + `roles`의 키와 같아야 하고, 규칙이 이를 확인한다.

이름은 관리자만 바꾼다(규칙의 `ownerManages`, 앱의 `Ledger.canRename`). 앱은 이름과 `updatedAt`만 쓴다(`ledgerRenameUpdate`).

`months`(항목 있는 달 목록)는 관리자·편집자가 달을 더하기만 한다(규칙의 `recordsMonths`). 빼거나 다른 칸과 같이 고칠 수 없고,
값은 겹치지 않는 `yyyy-MM`이며 1,200개까지다. `updatedAt`은 바꾸지 않는다.

- 새 가계부는 빈 목록(`[]`)으로 만든다(`newLedgerData`). 만들 때 달을 미리 넣을 수는 없다.
- 그달에 처음 항목을 넣을 때 항목·변경 기록과 같은 일괄 쓰기로 `arrayUnion`한다(`recordMonthUpdate`, `EntriesRepository.add`의 `recordMonth`).
  고정 지출로 그달을 채울 때도 같은 트랜잭션에서 더한다. 이미 있으면 바뀌지 않는다.
- 달력에서 가계부가 없는 달의 가계부를 만들면(`EntriesNotifier.addMonth`) 반복 설정으로 그달 고정 지출을 채우면서(지난 달은 채우지 않음) 그달을 더한다.
  `fillPlanned`의 `recordMonth`라 고정 지출이 없거나 이미 다 있어도 더하고, 한 트랜잭션이라 온라인에서만 된다.
- 휴지통에 넣거나 완전히 지워 그달 항목이 없어져도 목록에서 빼지 않는다.
- `months`가 생기기 전(2026-10-26 이전)에 만든 가계부는 쓰기 권한이 있는 사람이 앱을 열 때 한 번 모아 적는다
  (`MonthsBackfillNotifier`). 만든 달 1년 전부터 이번 달 1년 뒤까지 달마다 네 컬렉션을 한 건씩 서버에서 읽고(25달이면 읽기 100번),
  찾은 달을 지금 목록과 합쳐 적는다. 하나도 없으면 빈 목록을 적어 다시 모으지 않는다. 그 전까지 앱은 달을 가리지 않는다.

### `invites/{code}`

문서 id가 초대 코드다. 앱이 추측하기 어려운 무작위 문자열로 만든다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `ledgerId` | string | 초대할 가계부 |
| `role` | `'editor'` \| `'viewer'` | 들어오면 받을 역할 |
| `createdBy` | string | 만든 관리자 uid |
| `createdAt` | timestamp | 서버 시간 |
| `expiresAt` | timestamp | 만든 때부터 7일 이내 |

- 코드를 아는 사람만 한 건씩 읽을 수 있고, 목록 조회는 막는다.
- 관리자만, 자리가 남은(혼자인) 가계부에만 만들 수 있다.
- 유효기간 안에는 다시 쓸 수 있지만, 가계부가 두 명으로 차면 더는 들어올 수 없다. 관리자가 지우면 바로 못 쓴다.

참여는 가계부 문서 하나를 고치는 것으로 한다(자리가 남아 있을 때만): `memberUids`에 자기 uid 추가, `roles`에 초대의 역할로 자기 추가, `inviteCode`에 코드, `updatedAt`에 서버 시간.

### 가계부 설정: `members`, `categories`, `paymentMethods`, `templates`

가계부를 만들 때 가계부 문서와 **같은 일괄 쓰기(WriteBatch)** 로 이름표 두 장, 기본 분류, 기본 결제수단을 넣는다
(`LedgerRepository.create`, 기본값은 `defaultSettingDocs`). 설정을 만드는 규칙은 `getAfter`로 일괄 쓰기가 끝난 뒤의
가계부를 보고 권한을 확인한다. 그래서 아직 없는 가계부의 설정도 같은 일괄 쓰기 안에서는 만들 수 있고, 남의 가계부에는 만들 수 없다.

규칙은 공통 기록 필드와 이름표의 id·이름 길이, 분류(`validCategory`)·결제수단(`validPaymentMethod`)·고정 지출(`validTemplate`)의
받는 필드와 값을 확인한다. 앱의 모델은 [`lib/domain/model`](../lib/domain/model), 읽기·쓰기 변환 함수는 `lib/data/settings/firestore_settings_repository.dart`에 있고,
읽을 때 모르는 값은 앱이 건너뛴다.

- 이름표·분류·결제수단은 **지울 수 없다**(규칙이 `templates`만 지우게 한다). 지난 항목이 이 id를 가리키고 있어서, 지우면 카드로 쓴 돈이
  현금 유출로 바뀌고 저축 분류의 합계가 빠져 지난 달 숫자가 바뀐다. 분류·결제수단은 대신 숨긴다(`hidden`).
- 설정은 관리자·편집자가 바꾸고 온라인에서만 된다. 쓰기는 모두 트랜잭션이라 연결이 없으면 실패한다(`SettingsWriteFailure.offline`).
  설정·고정 지출을 바꿀 때도 변경 기록을 같은 트랜잭션으로 남긴다(아래 `activity`).
- 같은 목록 안의 이름 겹침은 규칙이 다른 문서를 볼 수 없어서 앱이 막는다(숨긴 것 포함).

**`members/{owner|partner}`**: 두 사람의 이름표

| 필드 | 타입 | 설명 |
|---|---|---|
| `name` | string (1~10자) | 화면에 보일 이름. 관리자는 로그인 이름(10자까지, 없으면 '나'), 상대는 '상대'로 시작한다 |

- 문서 id는 `owner`(관리자)와 `partner`(초대로 들어온 사람) 두 개뿐이다(규칙의 `validMember`, 앱의 `MemberSlot`).
- 항목의 '누가'는 이 id로 적는다. 그래서 상대가 들어오기 전에도 상대 몫을 적을 수 있다.
- 관리자·편집자가 두 장 모두 이름을 바꿀 수 있다(`memberRenameUpdate`). 이름표가 없는 옛 가계부는 이름을 처음 바꿀 때 만든다(`newMemberData`).

**`categories/{id}`**: 지출 분류

| 필드 | 타입 | 설명 |
|---|---|---|
| `name` | string (1~20자) | 분류 이름. 같은 가계부 안에서 겹치지 않는다(앱이 막음) |
| `countsAsSaving` | bool | 이 분류의 고정 지출을 월 요약의 '저축'에 넣을지 |
| `order` | int (0 이상) | 보여줄 순서. 앱이 정렬한다(없으면 맨 뒤). 새로 더하면 지금 개수(맨 뒤) |
| `hidden` | bool (선택) | 숨긴 분류. 새 항목·고정 지출에서 고를 수 없고, 월 요약에는 그달에 쓴 항목이 있을 때만 보인다. 지난 항목과 합계에는 그대로 쓰인다 |

기본값은 시트와 같은 4개다: 대출원금(저축), 대출이자, 저축/투자(저축), 소비.
앱의 쓰기 데이터는 `newCategoryData`, `categoryUpdateData`(이름·저축 집계), `settingHiddenUpdate`(숨기기·다시 보이기)다.

**`paymentMethods/{id}`**: 결제수단

| 필드 | 타입 | 설명 |
|---|---|---|
| `name` | string (1~20자) | 결제수단 이름. 같은 가계부 안에서 겹치지 않는다(앱이 막음) |
| `kind` | `'account'` \| `'autoTransfer'` \| `'card'` | 계산에서는 카드인지만 본다. 만든 뒤에는 바꿀 수 없다(규칙의 `keepsKind`) |
| `order` | int (0 이상) | 보여줄 순서 |
| `hidden` | bool (선택) | 숨긴 결제수단. 새 항목·고정 지출에서 고를 수 없지만, 그 결제수단으로 쓴 돈은 그대로 계산한다(숨긴 카드도 카드 사용분) |

기본값은 공동 통장(`account`)과 자동이체(`autoTransfer`)다. 카드는 사람마다 달라 설정 탭에서 카드마다 하나씩 추가한다.
앱의 쓰기 데이터는 `newPaymentMethodData`, `paymentMethodRenameUpdate`(이름만), `settingHiddenUpdate`다.

**`templates/{id}`**: 고정 지출의 반복 설정. 매달 나가는 돈이고, 이것으로 달마다 고정 지출 항목(`months/{달}/planned/{같은 id}`)을 만든다

| 필드 | 타입 | 설명 |
|---|---|---|
| `title` | string (1~40자) | 이름. 그달 고정 지출의 제목이 된다 |
| `amount` | int (0 이상, 선택) | 매달 금액(원). 없으면 금액 미정 |
| `categoryId` | string | 분류 문서 id |
| `paymentMethodId` | string | 결제수단 문서 id |
| `memberId` | `'owner'` \| `'partner'` | 누구 몫인지 |
| `dueDay` | int (1~31) | 매달 예정일. 31은 말일이고, 그달에 없는 날(2월 30일)은 그달 말일이 된다 |

- 규칙(`validTemplate`)이 위 필드와 공통 기록 필드만 받고 값의 범위를 확인한다. 앱의 쓰기 데이터는 `newTemplateData`·`templateUpdateData`
  (`lib/data/templates/firestore_templates_repository.dart`, 고칠 때 비운 금액은 `FieldValue.delete()`)다.
- 반복 설정만 따로 바꾸는 화면은 없다. 항목 탭에서 고정 지출을 더하거나 고치거나 그만하면 반복 설정과 그달 항목을 한 트랜잭션으로 바꾼다
  (`TemplatesRepository.add`·`update`·`stop`·`resume`). 연결이 없으면 실패한다.
  - 더하기: 반복 설정과 보고 있는 달의 항목을 같은 id로 만들고, 이미 만들어진 뒤 달(가계부의 `months` 가운데 그 달보다 뒤)에도 지급 전 항목을 만든다(`laterEntryDraft`).
  - 고치기: 그달 항목은 고친 값 전체로, 반복 설정은 그달만 바뀌는 칸(금액·지급·메모)을 뺀 값으로 쓴다. 뒤 달의 지급 전 항목은
    반복 설정이 정하는 칸(제목·분류·결제수단·누가·예정일)만, 금액은 반복 설정의 금액이 바뀌었을 때만 맞춘다(`laterEntryUpdate`).
  - 그만하기: 반복 설정을 지우고 그달 항목(지급 전이면)과 뒤 달의 지급 전 항목을 휴지통에 넣는다(`purgeAt` 30일). 앞의 달과 지급한 항목은 남는다.
  - 되돌리기: 반복 설정을 같은 id로 다시 만들고 그때 휴지통에 넣은 항목을 꺼낸다.
- 반복 설정이 없는 옛 고정 지출(+ 버튼으로 직접 더하던 시절의 항목)은 다른 항목처럼 고치고 휴지통에 넣는다.

설정 문서가 생기기 전(2026-10-22 이전)에 만든 가계부에는 이름표가 없다. 앱은 이름표가 없으면 역할 이름('관리자', '상대')으로 보여준다.

### 가계부 항목: `months/{yyyy-MM}/incomes|planned|extras|cardBills`

- 한 달은 달력 1일~말일이다(앱의 `YearMonth`).
- 달 문서(`months/{yyyy-MM}`) 자체는 만들지 않고 하위 컬렉션만 쓴다. 달 id는 `2026-10` 형식이어야 한다.
- `planned`의 문서 id는 템플릿 id다. 두 사람이 동시에 그달을 처음 열어도 같은 문서를 만들어 중복이 생기지 않는다.
  2026-10-29 이전에 + 버튼으로 직접 더한 고정 지출은 반복 설정이 없는 새 id다.
- `amount`: 0 이상의 정수(원). `planned`만 비어 있을 수 있다(금액 미정).
- `deletedAt`: 휴지통에 넣은 시간. 비어 있으면 정상 항목. **휴지통에 있는 항목만 완전히 지울 수 있다.**
  - 휴지통에 넣을 때만 서버 시간으로 쓰고, 꺼낼 때는 필드를 지운다(`FieldValue.delete()`). `null`로 쓰지 않는다.
  - 방금 넣어 아직 서버에 닿지 않은 문서는 서버 시간이 null로 읽힌다. 앱은 고친 내용이 서버에 닿기 전이면
    필드가 있기만 해도 휴지통으로 본다(`entryIsTrashed`).
- 휴지통 항목은 합계에서 뺀다. 앱은 그달 네 컬렉션을 구독해 휴지통 항목을 앱에서 거른다
  (`where('deletedAt', isNull)`은 필드가 없는 문서를 빼 버린다). 휴지통 항목도 읽기 횟수에 들어간다.
  걸러 낸 휴지통 항목은 `MonthLedger.trashed`에 모아 휴지통 화면이 그대로 쓴다. 그래서 휴지통은 보고 있는 달만 보여주고 읽기가 늘지 않는다.
- `purgeAt`: 자동으로 지울 때. 휴지통에 넣을 때 앱이 지금부터 30일 뒤로 적고(`trashEntryUpdate`), 꺼낼 때 `deletedAt`과 함께 지운다.
  이 시각이 지나면 Firestore TTL 정책(`firestore.indexes.json`의 `fieldOverrides`)이 문서를 지운다. TTL은 보통 하루 안에 지우고, 정확한 시각을 보장하지 않는다.
  - 규칙은 `purgeAt`을 timestamp로만, 그리고 `deletedAt`이 있을 때만 받는다. 휴지통 밖의 항목은 TTL로도 지워지지 않는다.
  - 반복 설정이 남아 있는 이번 달 이후의 고정 지출은 완전히 지우면 그달을 다시 열 때 다시 만들어진다.
    그래서 `purgeAt`을 적지 않고, 휴지통 화면도 완전 삭제 단추를 숨긴다(`staysInTrash`, 반복 설정 id로 판단). 지난 달이 되거나
    고정 지출을 그만하면(반복 설정이 지워짐) 지울 수 있다.
  - 자동 삭제를 넣기 전(2026-10-23 이전)에 휴지통에 넣은 항목에는 `purgeAt`이 없어 자동으로 지워지지 않는다.
- 완전 삭제는 휴지통 화면에서만 한다(`EntriesRepository.purge`, 트랜잭션). 서버에서 읽어 휴지통에 있을 때만 지운다.

규칙(`validEntry`)은 아래 표의 필드만 받고(종류마다 `keys().hasOnly`), 만들 때와 고칠 때 모두 고친 뒤의 문서 전체를 본다.

- `memberId`는 `owner`·`partner`만, 표에서 ✓인 id 칸(`categoryId`·`paymentMethodId`·`cardId`)은 비지 않은 문자열이어야 한다.
- `title`은 카드 대금 말고 꼭 있어야 하고 1~40자, `memo`는 200자까지, 날짜는 `yyyy-MM-dd` 형식 문자열이다.
  규칙의 문자열 길이는 UTF-16 단위로 세서 이모지는 한 개가 두 글자다. 앱도 `String.length`로 센다(`entryTitleMaxLength`).
- 앱의 쓰기 데이터는 `newEntryData`·`entryUpdateData`(고칠 때 비운 칸은 `FieldValue.delete()`)·`trashEntryUpdate`·`restoreEntryUpdate`다.
  쓸 때마다 변경 기록을 같은 일괄 쓰기·트랜잭션으로 남긴다(아래 `activity`).
- 그래도 앱은 읽을 때 계산에 쓰는 값(누가·금액·분류·결제수단·카드)이 없거나 잘못된 문서는 건너뛰고, 제목·메모·날짜는 잘못돼도 비워 두고 항목을 살린다.

오프라인에서는 새 항목만 더할 수 있다(`docs/plan.md`). 앱은 새 항목을 서버 응답을 기다리지 않고 기기 캐시에 넣고,
서버가 나중에 거부하면(`permission-denied`) 저장소의 `rejectedAdds`로 알려 홈 화면이 스낵바로 알린다(항목은 목록에서 빠진다).
새 항목과 그 변경 기록은 한 번의 일괄 쓰기라 오프라인에서 같이 쌓이고, 서버가 거부하면 같이 빠진다.
고치기·휴지통·꺼내기·완전 삭제는 트랜잭션으로 해서 연결이 없으면 실패하게 하고, 그사이 상대가 휴지통에 넣은(꺼낸) 항목은 고치지 않는다.

| 필드 | `incomes` | `planned` | `extras` | `cardBills` | 설명 |
|---|---|---|---|---|---|
| `memberId` | ✓ | ✓ | ✓ | ✓ | 누구 몫인지. 이름표 id(`owner`·`partner`) |
| `amount` | ✓ | 비울 수 있음 | ✓ | ✓ | 0 이상의 정수(원) |
| `title` | ✓ | ✓ | ✓ | | 항목 이름 |
| `categoryId` | | ✓ | | | 분류 문서 id |
| `paymentMethodId` | | ✓ | ✓ | | 결제수단 문서 id. 카드면 그달 현금 유출이 아니라 다음 달 청구 예정이다 |
| `cardId` | | | | ✓ | 출금된 카드의 결제수단 문서 id |
| 날짜 | `receivedOn` 받은 날 | `paidOn` 지급한 날 | `spentOn` 쓴 날 | `paidOn` 출금일 | `2026-10-25` 형식 문자열(선택). 날짜만 필요해서 두 사람의 시간대가 달라도 바뀌지 않게 문자열로 둔다 |

### 반복 설정으로 그달 고정 지출 만들기

- 요약·항목 탭에서 **이번 달이나 다음 달**을 보면, 그달에 아직 없는 반복 설정의 고정 지출을 만든다(홈 틀의 `MonthFillNotifier`).
  지난 달과 다음 달보다 먼 달은 만들지 않는다(그달에서 고정 지출을 더하면 그달부터 생긴다). 달 목록(`months`)이 있는 가계부는 탭이 오가는 달
  (목록의 달·이번 달)만 채워서, 달력으로 다음 달을 지나가기만 해서는 그달이 생기지 않는다. 다음 달은 대개 아래 경우로 채운다.
- 달력에서 가계부가 없는 달의 가계부를 만들면, 이번 달 이후의 달이면 그때 반복 설정으로 그달을 채운다.
  지난 달은 채우지 않고 달만 만든다(`fillsTemplatesOnAdd`).
- '아직 없는'은 그달 `planned`에 그 템플릿 id의 문서가 없다는 뜻이다. 휴지통에 넣은 문서도 있는 것으로 보고 다시 만들지 않는다.
  고정 지출을 더하거나 고치면 이미 만들어진 뒤 달도 같은 트랜잭션으로 맞추고(위 `templates`), 아직 없는 달은 앞으로 만들 때 반복 설정 값을 쓴다.
- 앱은 그달 구독(`MonthLedger.plannedIds`, 휴지통 포함)으로 빠진 것을 고르고, 빠진 것이 있을 때만
  `EntriesRepository.fillPlanned` 트랜잭션에서 그 문서들을 서버에서 다시 읽어 없을 때만 만든다. 이미 있는 문서는 덮어쓰지 않는다.
  규칙으로도 이미 있는 문서를 새로 만드는 값(`createdNow`)으로 덮어쓸 수 없다.
- 만든 고정 지출은 지급 전이고, 제목·금액·분류·결제수단·누가와 그달 예정일(`dueOn`)을 옮긴다.
- 트랜잭션이라 오프라인에서는 만들지 못한다. 연결이 없으면 다음에 그달을 다시 볼 때 만든다.
- 반복 설정이 남아 있는데 휴지통의 고정 지출을 완전히 지우면 그 문서가 없어져 이번 달·다음 달이면 다시 만들어진다.
  그래서 반복 설정이 남아 있는 이번 달 이후의 고정 지출은 완전히 지우지 않고 휴지통에 남긴다(위 `purgeAt`).
- 그달을 자동으로 채우는 것은 변경 기록을 남기지 않는다. 먼저 연 사람의 이름으로 남아 헷갈리기 때문이다.

### 공통 기록 필드 (설정·항목 모두)

| 필드 | 만들 때 | 고칠 때 |
|---|---|---|
| `createdBy` | 내 uid | 바꿀 수 없음 |
| `createdAt` | 서버 시간 | 바꿀 수 없음 |
| `updatedBy` | 내 uid | 내 uid |
| `updatedAt` | 서버 시간 | 서버 시간 |

앱에서는 시간 필드에 `FieldValue.serverTimestamp()`를 넣어야 규칙을 통과한다.

### `activity/{id}`: 변경 기록

누가 언제 무엇을 바꿨는지 남긴다. 승인 방식 대신 변경 기록과 휴지통으로 두 사람의 신뢰를 지킨다(`docs/plan.md`의 '권한').

| 필드 | 타입 | 설명 |
|---|---|---|
| `actorUid` | string | 바꾼 사람 (내 uid만 가능). 화면에서는 가계부의 이름표로 보여주고, 나간 사람이면 '나간 구성원' |
| `at` | timestamp | 서버 시간 |
| `action` | string | `entry.create` 형식(영문.영문, 40자까지). 앱의 `ActivityAction` |
| `summary` | string (1~200자) | 무엇을 바꿨는지 한 줄. 예: `10월 추가 지출 '점심' 12,000원`, `분류 '여행' → '휴가' · 저축 집계 켬` |
| `expireAt` | timestamp | 지울 때(남긴 때부터 1년). TTL 정책이 지운다. 규칙은 요청 시각보다 뒤이고 400일 이내만 받는다(오프라인에서 남겨 나중에 올라가는 기록도 받게 하한은 넉넉히 둔다) |

- 추가만 가능하고 고치거나 지울 수 없다. 관리자·편집자만 남기고, 보기 전용을 포함한 구성원은 모두 읽는다.
- 앱은 항목·고정 지출·설정을 쓰는 저장소에서 같은 일괄 쓰기·트랜잭션으로 남긴다(`newActivityData`, 요약은 `lib/domain/activity/activity_summary.dart`).
  그래서 기록과 실제 변경이 함께 쓰이거나 함께 실패한다. 규칙은 기록이 같이 쓰였는지까지는 확인하지 않는다.
- 남기는 동작: 항목 추가·고치기·휴지통·되살리기·완전 삭제, 고정 지출 추가·고치기·삭제·되돌리기,
  가계부 이름·이름표 이름 바꾸기, 분류·결제수단 추가·고치기·숨기기·다시 보이기.
- 요약에는 종류·제목·금액이 들어가고, 고쳤으면 바뀐 칸 이름과 제목·금액의 앞뒤 값을 적는다. Firestore에만 저장하고 로그·Crashlytics에는 남기지 않는다.
- 읽기는 `orderBy('at', descending)`으로 최근 50건을 구독하고(변경 기록 화면이 열려 있을 때만), '더 보기'는 가장 오래된 기록의 시간 뒤로 50건씩 한 번 읽는다.
  단일 필드 정렬이라 복합 색인이 필요 없다. 서버에 닿기 전 기록은 시간이 null이고 맨 앞에 온다.

### `holidays/{yyyy}`: 공휴일

- 한 해에 문서 하나(`holidays/2026`). 달력이 날짜를 빨갛게 칠하고 이름을 알리는 데 쓴다.
- Cloud Functions `syncHolidays`(`functions/src/index.ts`)가 매일 새벽 4시(한국 시간)에 공공데이터포털
  '한국천문연구원_특일 정보'의 공휴일 조회(`getRestDeInfo`)로 올해와 내년을 받아 관리자 권한으로 쓴다.
  아직 발표 전이라 비어 있는 해는 쓰지 않고, 받은 값이 지금 문서와 같으면 다시 쓰지 않는다.
- 규칙: 로그인한 사람은 누구나 한 건씩 읽는다(`get`). 목록 조회와 앱에서의 쓰기는 막는다. 가계부와 상관없는 공개 정보라 구성원 확인을 하지 않는다.
- 앱은 달력이 보는 해의 문서 하나만 구독한다(`holidaysOfYearProvider`). 받지 못했으면 일요일만 빨갛다.

| 필드 | 설명 |
|---|---|
| `days` | `2026-10-03` 같은 날짜 → 공휴일 이름(`개천절`, `대체공휴일`). 같은 날 둘이면 `어린이날·부처님오신날` |
| `updatedAt` | 함수가 마지막으로 바꾼 서버 시간 |

## 비용 메모

- 휴지통 화면은 요약·항목 탭과 같은 그달 구독을 써서 따로 읽지 않는다. 변경 기록 화면은 열 때 최근 50건까지, '더 보기'마다 50건까지 읽는다.
- TTL 정책이 지우는 문서(휴지통 30일, 변경 기록 1년)도 삭제 횟수로 센다. TTL 필드(`purgeAt`, `expireAt`)는 색인하지 않는다.
- 하위 컬렉션 규칙은 가계부 문서를 한 번 읽어 권한을 확인한다. 이 읽기도 Firestore 읽기 횟수에 들어간다.
- 가계부를 지워도 하위 컬렉션은 남는다. 정리는 나중에 함수나 앱에서 처리한다.
- 보기 전용 구성원은 그달의 고정 지출을 만들 수 없다. 편집자나 관리자가 먼저 그달을 열어야 생긴다.
- 그달을 열 때마다 고정 지출 문서를 따로 읽지 않는다. 빠진 반복 설정이 있을 때만 그 문서 수만큼 트랜잭션에서 읽는다.
- 공휴일은 달력이 열려 있을 때 그해 문서 하나를 읽는다(해가 바뀌는 달로 넘기면 그해 것을 하나 더). 함수는 하루에 많아야 두 번 쓴다.
